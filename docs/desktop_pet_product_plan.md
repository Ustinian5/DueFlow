# DueFlow Desktop 桌宠 DDL 助手完整产品方案

## 1. 产品定位

DueFlow Desktop 是一个本地优先的桌面 DDL 管理助手。它以可交互桌宠作为常驻入口，帮助用户从截图、文字、文件、剪贴板、Webhook 等来源中识别 DDL 信息，自动整理成任务、日程、提醒和执行计划。

一句话定义：

> 一个有桌宠陪伴感的本地 DDL 管理助手，能看懂通知，帮用户排期，并在桌面上持续提醒用户完成任务。

这个产品不是通用聊天机器人，也不是单纯的日历工具。它的核心是面向 DDL 场景的信息理解、日程规划、风险提醒和桌面陪伴式交互。

## 2. 核心目标

最终产品需要解决三个问题：

1. 用户不想手动整理 DDL。
2. 用户经常忘记什么时候该做什么。
3. 普通日程工具太冷冰冰，不够主动、不够有存在感。

因此，产品最终要形成以下闭环：

```text
快速输入
  -> 智能理解
  -> 用户确认
  -> 自动排期
  -> 桌面提醒
  -> 桌宠互动
  -> 日历/列表管理
```

## 3. 产品形态

最终产品由三部分组成：

1. 桌宠悬浮入口
2. 主日程管理界面
3. 快速输入系统

### 3.1 桌宠悬浮入口

桌宠是产品的常驻入口，显示在桌面上，可以拖动、点击、右键操作。它不是装饰，而是任务状态的可视化表达。

桌宠需要具备：

- 常驻桌面
- 透明背景
- 可拖动
- 可隐藏
- 可切换形象
- 有多种表情和动作
- 根据 DDL 状态变化
- 点击后展开迷你任务面板
- 右键打开操作菜单
- 到点主动提醒
- 任务完成后反馈
- 支持拖拽文件到桌宠进行识别

桌宠状态至少包括：

- 空闲
- 思考中
- 开心
- 困惑
- 紧张
- 严肃提醒
- 庆祝
- 休息
- 催促

桌宠的价值是降低打开工具的成本，并让 DDL 状态在桌面上持续可见。

### 3.2 主日程管理界面

主界面是完整的 DDL 管理工作台，不是简单表格。它负责展示任务、日程、风险、原文依据和规划结果。

主界面需要包括：

- 今日任务
- 本周任务
- 月历视图
- 时间线视图
- Inbox 输入记录
- 风险任务
- 已完成任务
- 任务详情
- 原文依据
- LLM 抽取结果
- 日程计划
- 设置页

推荐信息结构：

```text
左侧：Inbox / Today / Week / Calendar / Risks / Settings
中间：日历视图 + 时间线
右侧：任务详情 + 原文依据 + 排期建议
底部：处理状态 / 快捷输入栏
```

主界面应该像日历工具和任务管理工具的结合体，但更适合 DDL 场景。

### 3.3 快速输入系统

用户应该可以用最少动作把信息丢进系统。

最终支持：

- 粘贴文字
- 拖拽文件
- 上传 PDF / Markdown / TXT / 图片
- 截图识别
- 剪贴板识别
- 快捷键唤起输入框
- Webhook 接入
- 本地 inbox 文件夹监听

输入完成后，系统不应直接静默入库，而是展示确认界面：

```text
我识别到：
- 任务名称
- 截止时间
- 提交物
- 提交方式
- 地点/平台
- 优先级
- 风险点
- 原文依据
```

用户可以确认、修改、删除或重新识别。

## 4. 核心使用流程

最终产品的完整流程：

```text
用户看到一条通知
  -> 截图 / 复制 / 拖文件给桌宠
  -> 系统提取文字
  -> LLM 抽取 DDL 信息
  -> 展示识别结果
  -> 用户确认
  -> 写入本地数据库
  -> 自动生成倒排计划
  -> 加入日历视图
  -> 桌宠根据状态变化
  -> 到时间主动提醒
  -> 用户完成后标记
  -> 桌宠反馈
```

系统必须保证关键字段可追溯。每一个任务名称、截止时间、提交物、提交方式都应该尽量保留原文依据。

## 5. 智能能力

LLM 在产品里承担“理解通知”的角色，而不是泛用聊天角色。

LLM 需要完成：

- 从长文本中识别任务
- 提取截止时间
- 判断截止时间置信度
- 提取提交物
- 提取提交方式
- 提取平台、地点、链接
- 识别缺失信息
- 提取原文依据
- 判断任务复杂度
- 估计完成所需时间
- 生成倒排计划
- 发现风险
- 生成每日执行建议

关键原则：

```text
LLM 抽取事实，系统负责确认和落库。
LLM 可以建议计划，但用户必须能修改。
所有关键字段必须保留原文依据。
```

建议将智能能力拆成两个阶段：

```text
extract：只抽取原文事实，不做过度推理。
plan：基于事实、当前日期、用户偏好生成计划。
```

这样可以降低幻觉风险，也便于在界面中展示“为什么系统这样理解”。

## 6. 日程系统目标

日程系统是产品核心，不是附属功能。

最终要支持：

- DDL 管理
- 任务拆解
- 自动倒排
- 今日计划
- 本周计划
- 月历查看
- 拖拽改期
- 冲突检测
- 风险高亮
- 提醒设置
- 完成状态
- 任务归档
- 重复任务
- 标签分类
- 优先级
- 临近截止提醒
- 逾期提醒
- 每日摘要

日历展示需要至少包含三种模式：

- 月历：查看 DDL 分布
- 周视图：查看近期压力
- 列表/时间线：查看执行顺序

任务状态至少包括：

- 待确认
- 待开始
- 进行中
- 已完成
- 已归档
- 已逾期

风险状态至少包括：

- 截止时间不明确
- 截止时间过近
- 缺少提交方式
- 缺少提交物
- 外部依赖
- 日程冲突
- 缺少最终检查

## 7. 桌宠交互目标

桌宠的价值是增加任务提醒的存在感，并形成轻量陪伴。

最终桌宠应该做到：

- 任务少时安静陪伴
- 任务临近时明显紧张
- 有任务完成时开心反馈
- 信息不完整时困惑提示
- 今日无任务时进入休息状态
- 高风险任务时主动弹气泡
- 点击可以快速查看今天要做什么
- 拖文件到桌宠身上即可识别，并按成功、重复、无草稿、解析失败、网络失败等结果给出分层反馈
- 截图识别时进入思考状态
- 识别成功后给出简短反馈
- 识别结果可以通过桌宠气泡再次打开主窗口并定位对应草稿或 Inbox 记录
- 未生成任务草稿时可以直接跳转、高亮并滚动到对应 Inbox 记录
- 拖拽解析失败时显示本轮失败次数，并提示修正后重新拖入
- 解析或抽取失败的 Inbox 记录可以一键重试
- 重复输入需要显示原始 Inbox 记录，并能一键定位

桌宠可以有简短文本气泡，但不应变成泛用聊天窗口。

### 7.1 桌宠状态机

桌宠动作必须由统一运行时调度，具备开始、重试、完成、失败、阻断等生命周期反馈，并对重复点击、桌面命令失败和第三方扩展能力保持可控边界。

建议定义如下状态机：

```text
no_task        悠闲
processing     思考
task_created   开心
deadline_near  紧张
missing_info   困惑
task_done      庆祝
overdue        严肃提醒
night_idle     犯困
```

状态由任务数据驱动，而不是随机播放。比如：

- 今日无任务：`no_task`
- 正在识别输入：`processing`
- 新任务成功入库：`task_created`
- 三天内有高优先级 DDL：`deadline_near`
- 任务缺少截止时间或提交方式：`missing_info`
- 用户完成任务：`task_done`
- 有逾期任务：`overdue`

## 8. 视觉与体验目标

最终产品应该是轻量、亲切、细腻的桌面工具。

视觉方向：

- 桌宠可爱但不幼稚
- 主界面清爽、实用、信息密度适中
- 日历风格明确
- 风险状态一眼可见
- 动效轻，不打扰
- 反馈明确
- 桌宠和界面视觉统一

桌宠形象必须原创，不直接模仿 QQ 宠物或其他已有 IP 的具体形象。可以借鉴“桌面陪伴式入口”的产品形态，但角色设定、造型和视觉资产必须独立设计。

可选角色方向：

- DDL 小助教
- 时间管理员
- 日程精灵
- 桌面秘书
- 学业助手
- 电子伴学角色

桌宠资产演进方向：

```text
第一层：多状态 PNG
第二层：Sprite Sheet 小动画
第三层：Live2D / Spine 风格角色
```

桌宠形象必须采用 manifest-first 方式导入和审计。每个形象包需要声明稳定 ID、名称、作者、版本、许可证、默认缩放、尺寸、缩略图、默认资产和状态资产；本地资源路径必须限制在形象包内，不能引用远程 URL 或越界路径。当前桌面壳会扫描 `pets/` 投放目录，启用时把 manifest 和声明的图片资产复制到 `pets-active/<id>-<version>/` 受控目录，并通过 staging 目录完成替换，失败时保留原启用副本。授权确认会记录受控 manifest 路径、确认时的 license 文本和确认时间。设置页会优先使用 manifest 声明的缩略图做预览，并缓存本地资产 URL；运行时如果选中形象丢失、校验失败或未授权，桌宠会回退内置形象并在气泡中提示原因。

产品初期不强依赖复杂动画。核心功能稳定后，再投入更高级的角色资产制作。

## 9. 输入体验目标

产品的吸引力很大程度取决于输入是否足够顺手。

最终输入方式：

```text
快捷键截图
剪贴板识别
拖拽文件
手动输入
Webhook
本地文件夹监听
```

推荐快捷键：

- `Option + Shift + D`：截图识别 DDL
- `Option + Shift + V`：读取剪贴板并提取
- `Option + Shift + Space`：唤出快速输入框
- `Option + Shift + T`：显示今日任务

截图识别流程：

```text
用户按快捷键
  -> 桌宠变 thinking
  -> 选择截图区域
  -> OCR / Vision LLM 识别文字
  -> 结构化抽取任务
  -> 展示确认面板
  -> 用户确认入库
  -> 自动排期
  -> 桌宠反馈
```

## 10. 隐私与本地化目标

这个产品应该强调本地优先。

最终目标：

- 数据默认保存在本地 SQLite
- 用户输入、任务、计划都在本机
- API Key 存本地配置
- 支持 mock 模式
- 支持用户选择真实模型
- 支持导出数据
- 支持清空数据
- 不强制联网
- 不上传用户文件，除非用户启用云端 LLM

隐私说明必须在设置页中明确展示：

- 哪些数据保存在本地
- 哪些数据会发送给模型服务
- 如何关闭云端模型
- 如何删除本地数据
- 如何导出备份

本地优先是产品可信卖点，尤其适合学生、个人用户处理课程、比赛、实习、申请等敏感信息。

现有模型：

- `InboxItem`
- `TaskItem`
- `PlanItem`
- `RiskItem`
- `ExportRecord`

建议新增模型：

- `PetState`
- `Reminder`
- `Attachment`
- `ScreenshotInput`
- `TaskRevision`
- `UserPreference`
- `TaskTag`
- `TaskEvidence`

任务字段建议增强：

- `estimated_effort`：预计耗时
- `recurrence`：是否重复
- `reminder_times`：提醒时间
- `tags`：课程 / 比赛 / 实习 / 个人
- `confidence`：总体置信度
- `user_confirmed`：用户是否确认
- `source_url`：来源链接
- `attachments`：关联附件
- `last_planned_at`：最近一次规划时间

## 14. 产品吸引力

最终产品的核心吸引点：

### 14.1 快

用户截图或复制一段通知，几秒内变成 DDL 任务。

### 14.2 准

每个关键字段都有原文依据，用户能确认和修改。

### 14.3 主动

不是等用户打开应用，而是桌宠在桌面上持续反馈状态。

### 14.4 有陪伴感

任务不是冷冰冰躺在表格里，而是通过桌宠表情和提醒变得可感知。

### 14.5 本地优先

适合学生、个人用户处理课程、比赛、实习、申请等敏感信息。

## 15. 产品边界

最终产品不应偏离 DDL 管理主线。

明确不做或暂不做：

- 不做泛用聊天机器人
- 不做多人协作平台
- 不做复杂企业工作流
- 不做社交系统
- 不直接复制已有 IP 形象
- 不强制云端存储
- 不默认上传用户文件

桌宠可以增强情绪反馈和陪伴感，但不能喧宾夺主。核心仍然是 DDL 管理、日程规划和提醒。

## 16. 最终愿景

DueFlow Desktop 最终应该成为：

> 一个能从截图和通知里自动读出 DDL、帮用户排好计划，并用桌宠在桌面上陪用户完成任务的本地日程助手。
